# Dime API (`api/`)

TypeScript + [Hono](https://hono.dev) on Cloudflare Workers. The whole backend is this one Worker. The HTTP API follows contracts C1-C8 (originally set by a Python FastAPI backend, since removed).

## Architecture

| Concern | Where |
| --- | --- |
| Database | **D1** binding `DB`, schema in `migrations/` (`0001_init`, `0002_auth`, `0003_ai_usage`), raw prepared SQL through `core/db.ts` |
| Sign-in | Own Google sign-in: `POST /api/v1/auth/google` checks the Google ID token (audience `GOOGLE_WEB_CLIENT_ID`) and returns HS256 sessions (`AUTH_JWT_SECRET`); `/auth/refresh` rotates refresh tokens, `/auth/sign-out` revokes |
| Files | **R2** binding `MEDIA` (bucket `dime-media`): avatars public, receipts and voice via HMAC-signed `/media/*` links (`MEDIA_URL_SECRET`) |
| Voice / receipt OCR | **Workers AI** binding `AI` (Whisper, Llama 4 Scout) with a daily neuron cap (`AI_DAILY_NEURON_CAP`, `AI_USER_DAILY_RECEIPTS`, `AI_USER_DAILY_VOICE`), optional AI Gateway |
| Parsing + agent | DeepSeek (`DEEPSEEK_API_KEY`) |
| Live updates | Durable Object `UserHub` (binding `USER_HUB`), one per user, WebSocket at `GET /api/v1/realtime` |
| Background | Queues `dime-ingest` (+ DLQ `dime-ingest-dlq`) and `dime-email`; crons `*/5 * * * *` (ingest recovery sweep) and `30 2 * * *` (email digest fan-out) |
| Email | Brevo; images from Workers Static Assets (`public/email`, binding `ASSETS`) |
| OTA updates | Self-hosted Expo Updates (protocol v1) at `/api/v1/updates/{manifest,assets/:hash}`, public; manifests are signed offline by `frontend/scripts/publish-update.mjs` and stored in R2 under `updates/` (layout in `src/features/updates/storage.ts`); see `../docs/RELEASE.md` |
| Limits | Rate limits `WRITE_LIMITER`, `AI_LIMITER`; smart placement near D1 |

## Local development

Requires Node 22+. Deploying: see [`DEPLOY.md`](DEPLOY.md); the ordered go-live list is `../docs/rewrite/GO-LIVE.md`.

```bash
cd api
npm install
cp .dev.vars.example .dev.vars   # fill in the keys
npm run dev                      # wrangler dev -> http://127.0.0.1:8787
```

- Non-secrets live in `wrangler.jsonc` `vars` (replace the `REPLACE-ME` placeholder); `.dev.vars` overrides them locally. Secrets are set with `wrangler secret put NAME`.
- D1, R2, queues, the Durable Object and rate limits run locally in Miniflare (state in `.wrangler/state`). Create the local schema once and after each new migration: `npx wrangler d1 migrations apply DB --local`. Load the agent fixture if you want it: `npx wrangler d1 execute DB --local --file evals/seed.sql`.
- The `AI` binding is `remote: true`: local `wrangler dev` calls the real Workers AI (needs `wrangler login`; counts toward the free allowance). Everything else stays local.
- Sign-in needs `AUTH_JWT_SECRET` and a real Google ID token for `GOOGLE_WEB_CLIENT_ID`; the tests mint tokens themselves (`test/helpers.ts`).
- After editing `wrangler.jsonc` run `npm run cf-typegen` (regenerates `worker-configuration.d.ts`, which is committed).

## Structure

```
src/
  index.ts          default export { fetch, queue, scheduled }
  app.ts            builds the Hono app, mounts feature routers under /api/v1
  core/             cross-cutting infrastructure only (no business logic)
    env.ts          Bindings/Variables types + zod-validated, memoized config (getConfig)
    errors.ts       AppError hierarchy, onError (C8), notFound
    request-id.ts   X-Request-ID middleware + access log line
    logging.ts      structured JSON log (log.info/warn/error), AsyncLocalStorage request id
    auth.ts         requireAuth (Worker-issued HS256 JWT via jose), currentUser(c)
    db.ts           getDb(c) and thin typed helpers over D1 (first / all / run / batch)
    db-errors.ts    unique-violation detection, typed not-found / forbidden errors
    http.ts         fetchJson / fetchWithRetry (timeout, bounded retries, UpstreamError)
    validation.ts   validate(target, schema): zod validator with FastAPI-style 422
    body-limit.ts   limitBody / limitUpload (413)
    cors.ts         CORS only when CORS_ORIGINS is non-empty
    rate-limit.ts   rateLimit('WRITE_LIMITER' | 'AI_LIMITER')
  features/<feature>/
    routes.ts       Hono router: parse/validate, call service, shape response
    schemas.ts      zod schemas (request + response) and inferred types
    service.ts      business logic (pure where possible)
    repository.ts   all D1 access for the feature
test/               Vitest specs (run in workerd)
public/email/       static email images, served as /email/* by Workers Static Assets
```

## Adding a feature

1. Create `src/features/<name>/{routes,schemas,service,repository}.ts`.
2. In `routes.ts` export a `new Hono<AppBindings>()` router. Protect it with `router.use(requireAuth)`; add `rateLimit('WRITE_LIMITER')` on mutating routes and `rateLimit('AI_LIMITER')` on LLM routes (after `requireAuth`).
3. Validate input with `validate('json' | 'query' | 'param', schema)` and read it with `c.req.valid(...)`. Do not use `zValidator` directly (the wrapper produces the FastAPI-compatible 422).
4. Throw `AppError` subclasses (`NotFoundError`, `ConflictError`, `ValidationError`, ...) from services/repositories; never `try/catch` in routes just to map errors. Anything else becomes a 500 `{"detail":"Internal error","request_id"}` (C8).
5. Get the database with `getDb(c)` and pass it (and `user.id`) into services. Always filter by the JWT user id: D1 has no row level security, so every query binds `user_id`.
6. Read config with `getConfig(c.env)`; add new env vars to the zod schema in `core/env.ts`, `wrangler.jsonc` `vars` and `.dev.vars.example`.
7. Mount the router in `src/app.ts` with `api.route('/<name>', router)`.
8. Outbound HTTP (DeepSeek, Brevo, FavQs, Expo) goes through `fetchJson`/`fetchWithRetry`. Do not retry non-idempotent calls unless the provider supports it.
9. Background work: `c.executionCtx.waitUntil(...)` for small fire-and-forget tasks, Queues for anything slow or retryable.
10. Add tests in `test/` (`app.request(path, init, env)` with `makeEnv()`/`signToken()` from `test/helpers.ts`).

## Testing: real local D1 + an outbound HTTP stub

Relational data lives in **D1** (binding `DB`, schema in `migrations/`, applied with `wrangler d1 migrations apply DB [--local|--remote]`). Tests run against a real local D1: `vitest.config.ts` reads `migrations/` (`readD1Migrations`), `test/setup.ts` applies them once per file and `resetDb()` empties every table (system categories stay) and re-seeds the default user before each test. `test/db.ts` has the seed helpers (`seedTransaction`, `seedCategory`, `seedJob`, ...), `rowsOf` / `oneRow` for database-state assertions, and wrappers that break chosen statements (`failingOn(/INSERT INTO jobs/)`, `failingDb('batch')`, `withBeforeExec`, `spyDb`). Every table references `users(id)`, so a test user must exist (`USER_ID` is seeded).

`test/supabase-stub.ts` (the name is historical) replaces `globalThis.fetch` for the **outbound HTTP** that is not in D1 (Brevo, Expo, DeepSeek, FavQs); the Workers AI binding is faked with `FakeAi` (`test/ingest-fixtures.ts`), since miniflare cannot run it (`remoteBindings: false` in `vitest.config.ts`):

```ts
const stub = useSupabaseStub();                       // describe level: fresh stub per test
stub.on('POST', '/v3/smtp/email', () => json({...}));   // route by method + path substring/regex
const res = await call('/api/v1/categories', { method: 'PATCH', json: {...} });   // test/helpers.ts: signs a JWT for USER_ID
expect(stub.last('POST', '/v3/smtp/email').body).toMatchObject({...});
```

Helpers: `json`, `makeCtx()` (collects `waitUntil` promises; pass to `call` as 3rd arg and `await flush()`). Matching is on path only (not host); unmatched requests return a 599.

Conventions: repositories take a `Db` (`core/db.ts`, a thin typed layer over D1: `first` / `all` / `run` / `batch`, no ORM); ids are text uuids made in the Worker, money is integer cents (`decimalToCents` / `formatCents` at the repository boundary), timestamps are `toISOString()` text, booleans 0/1, JSON text. `transactions.payee_key` is computed on write (`payeeKey` in `transactions/dedupe.ts`). `core/db-errors.ts` recognises SQLite unique violations and carries the not-found / forbidden codes of the atomic category + budget write. Media lives in R2 (binding `MEDIA`, `features/media/`): `storage.ts` (`mediaStore(env)`, `uploadMedia`, `downloadMedia`, local HMAC `signMediaUrls`), `routes.ts` (public `GET /media/*`: avatars public + cached, receipts/voice need `?exp&sig`), `refs.ts` (bare keys, Worker URLs and legacy Supabase URLs to keys). The origin of `/media` links is `EMAIL_PUBLIC_BASE_URL`; the secret is `MEDIA_URL_SECRET`. Tests use the real local R2 bucket (cleared per test in `test/setup.ts`). `core/decimal.ts`, `core/timestamps.ts` (`isoUtc`), `core/background.ts` (`defer`), `core/image-format.ts`, `validation.ts` `uuidString`/`unprocessable` are shared helpers. `requireAuth` is idempotent so routers sharing a prefix (`/me`, `/me/settings`, ...) verify the token once.

## Transactions (R2)

- `features/transactions`: list/detail/create/update/delete, home and month summary. `features/insights`: month insights. Shared pieces for R3: `transactions/service.ts` `createTransaction` (payment-hash dedupe + sparse merge, takes `detectedVia`/`receiptUrl`/`voiceUrl`), `features/media/*` (signing, upload, private path builder, magic-byte sniffing), `features/jobs/*` (jobs repository, `Idempotency-Key` parsing, `runIdempotent`), `features/notifications/{emitter,budget-evaluator,after-insert}.ts` (`notifyAfterInsert` is what the queue consumer calls after inserting a captured transaction).
- Aggregates are single `GROUP BY` queries on D1 (`transactions/repository.ts`); daily buckets are cut in TypeScript (`transactions/aggregates.ts`, `core/timezone.ts`) because SQLite has no IANA time zones.
- Timezone math is `core/timezone.ts` (Intl only). Ranges are always half-open `[from, to)` and sent to D1 as UTC instants.
- Money in responses is a 2-decimal string ("480.00"); empty days in daily series are "0", as in Python.
- Post-create budget evaluation, notifications and push run in `waitUntil` (`defer`): the 201 body never depended on them.

## Ingest pipeline: receipt / voice (R3)

- **Endpoints** (`features/ingest/routes.ts`, mounted at `/transactions`): `POST /receipt` (10 MB), `POST /voice` (15 MB). Both answer 202; the `timezone` query is validated up front (400). Receipt/voice: `limitUpload` (413), `Idempotency-Key` looked up BEFORE the body is read, magic-byte sniff (415; voice also refuses CAF: Whisper cannot read it and there is no ffmpeg), the Workers AI cap (`ai/neuron-cap.ts`: 429 + `Retry-After` until 00:00 UTC when today's neurons plus the estimate pass `AI_DAILY_NEURON_CAP`, or the user used today's `AI_USER_DAILY_RECEIPTS` / `AI_USER_DAILY_VOICE`, counted atomically per kind at accept time and given back if no job results; a replayed `Idempotency-Key` never counts), raw file to the PRIVATE R2 prefix, then ONE `jobs` row (`pending`, payload = object path only) and `INGEST_QUEUE.send({job_id, kind})`. If the queue send fails after the insert the request still succeeds and the row stays `pending` for the sweep.
- **Consumer** (`features/ingest/consumer.ts`, `queue()` in `index.ts` routes by queue name): per message `claimJob` (conditional pending -> processing, attempts + 1, max 3), download media, AI pipeline, `createTransaction` (server-set `detected_via` scan/voice and receipt/voice path), `notifyAfterInsert`, `markDone {transaction_id}`. Transient errors (AI/upstream 408/429/5xx, network, DB hiccup) on a non-final attempt release the job to `pending` and `message.retry({delaySeconds: 5 | 10 | 30})`; permanent errors or the 3rd attempt `markFailed` (<= 500 chars) + `capture_failed` notification (receipt `scan`, none for voice) and ack. A job whose attempts are already spent when its message arrives is failed and notified the same way. A `markDone` failure after the transaction was created is logged and the message acked (no AI re-run, no failure notice). `dime-ingest-dlq` has its own consumer that fails the job only if still unfinished, notifies, and acks. **Receipt OCR / voice:** the object is read from R2 and sent as bytes (base64 data URL / base64 audio) to Workers AI. Before the call the consumer re-checks the daily cap (over it: permanent failure + the usual capture-failed notification); after a successful call it books the neurons (actual `usage` / audio duration when the answer has it, else an estimate) with one upsert into `ai_usage`. Ingest `max_batch_size` is 5, processed one at a time (each job holds a whole media file in memory), and the consumer has `max_concurrency` 2.
- **Recovery sweep** (`features/ingest/sweep.ts`): cron `*/5 * * * *` calls `requeueStaleProcessing` + `listRecoverable` (updated_at older than 300 s, oldest first, 50 per kind) and re-sends the ids. `scheduled()` dispatches on `controller.cron`; `30 2 * * *` is the email-digest fan-out (R4, below).
- **AI** (`features/ai/`): `prompts.ts` (ported verbatim), `workers-ai.ts` (`env.AI.run`: Llama 4 Scout vision OCR and Whisper large-v3-turbo; the recorded audio is sent as-is; errors mapped to Transient/Permanent), `neuron-cap.ts` (neuron estimates, counters, upload and job guards), `deepseek.ts` (JSON mode, `AI_PARSE_FALLBACK` model chain, `AI_TIMEOUT_SECONDS` split across candidates), `parse-output.ts` (normalization + zod validation, port of `_parse_and_validate`), `service.ts` (`parseReceipt` / `parseVoice`). Errors are `TransientAiError` / `PermanentAiError` with generic messages; provider detail is only logged (S9). The agent (R4) reuses `ai/http.ts` (`aiPost`).
- **DB**: `0001_init.sql` has the unique partial index on `transactions (user_id, payment_hash)` (active rows). `createTransaction` resolves a unique violation to the winning row.
- **Tests**: `test/ingest-*.test.ts` and `test/ai.test.ts` use the outbound-HTTP stub, a real local D1 plus `FakeQueue` / `FakeMessage` (`test/ingest-fixtures.ts`); consumer functions take plain message objects.

## Daily limits and recurring items

- **Daily limits** (per user per UTC day; manual entry is unlimited): agent questions (`AGENT_DAILY_QUESTIONS`, 5), receipt scans (`AI_USER_DAILY_RECEIPTS`, 10), voice captures (`AI_USER_DAILY_VOICE`, 10), on top of the global neuron cap. Counters: `agent_usage.turns` and `ai_user_usage.receipts` / `voices` (migration `0005`), each claimed with one atomic upsert-with-`WHERE count < limit`. 429 + `Retry-After` until 00:00 UTC. `GET /api/v1/limits` (`features/limits`) returns `{resets_at, agent_questions, receipt_scans, voice_captures: {used, limit, remaining}, scanning_paused}` from one batch read.
- **Onboarding progress**: `GET /api/v1/me/onboarding-progress` (`features/onboarding`) returns `{first_expense, voice_or_scan, budget, recurring, asked_ai}` booleans from ONE statement of user-scoped `EXISTS` probes, for the app's Home "Get started" checklist. First expense = a live manual-or-other debit that is not a recurring posting; budget = monthly budget > 0 or any category budget; `asked_ai` = `users.first_agent_question_at` (migration `0009`, set when an agent turn answers, never when it is refunded).
- **Recurring items** (`features/recurring`, `/api/v1/recurring`, table `recurring_items`, migration `0006`): salary (`income`) and `subscription`s, monthly or yearly. `GET ?kind=` returns `{items, summary: {monthly_income_total, monthly_subscriptions_total}}`; `POST` (201, `post_current_period`), `PATCH /:id`, `DELETE /:id` (204). The `*/5` cron (`recurring/poster.ts`, next to the ingest sweep) posts every active item whose `next_due_date` at 06:00 in its timezone has arrived as a normal `manual` transaction (`transactions.recurring_item_id` marks the origin, `payment_hash = recurring:<item>:<date>` makes it idempotent), then advances ONE period (a backlog drains one period per run, 50 items per run). Day 29-31 clamp to the month's last day. Edits apply from the next posting; changing the schedule or resuming re-plans from today (never backfills, never double-posts a period already posted); deleting an item keeps its transactions. `GET /month?year=&month=` lists every item's occurrence in a calendar month with a status (`paid`: posted, with `transaction_id` and `posted_amount`; `skipped`: posted then deleted; `upcoming`: active, not posted, not before `next_due_date`; paused and unposted items are left out) plus fixed-money `totals`. **Fixed vs flexible**: a transaction is *fixed* when its category scope is `recurring_expense` / `recurring_income` (auto-posted or entered by hand, matching its type), *flexible* otherwise; month-summary, month-insights, home and day summaries carry the split (`fixed_*` / `flexible_*`), and month-insights' payee mix and top expenses are flexible only.

## Predictive engine and forecast

Plan: `../docs/PREDICTIVE-ENGINE-PLAN.md`. `features/engine/` keeps a per-user profile (`engine_patterns`, `payee_patterns`, migration `0010`) rebuilt nightly on the `dime-engine` queue; the forecast itself is computed on each request.

- **Forecast** (`GET /api/v1/forecast?year=&month=&timezone=`, `engine/routes.ts`, `service.ts`; maths in `forecast.ts`, `upcoming.ts`, `watch.ts`, template text in `copy.ts`): the current month returns `{year, month, today, timezone, mode, historyDays, landing, safeToday, categories, upcoming, watch, summary, accuracy}`. Money is a decimal string in rupees like every other response. `landing` = `{p10, p50, p90, budget, chanceUnder, spentSoFar, billsStillDue, flexibleRemaining}`: spent so far (every debit, the month summary's total) + recurring subscriptions still due this month + flexible spend still to come, resampled 1000 times from the same weekday's history (recent weeks weigh more, seeded by user and day so it is stable within a day). `chanceUnder` is the share of draws within the monthly budget (null without one; a budget of 0 is none). `mode` is `learning` (under 14 days of history: this month's daily rate, +-20%, no likely spends or unusual flags), `warming` (14-29 days: ranges 1.5x wider, weekdays with under 2 samples drawn from all days) or `full`; `widthFactor` in the profile scales the spread. `safeToday` = `{amount, usualForWeekday, weekday}` (amount is the budget left after bills, shared over today and the days after by weekday weight; null without a budget). `categories` lists spend-scope categories with `{id, name, iconName, color, spent, p50, budget, baseline, status: ok|hot|over}`. `upcoming` is the next 14 days: `bill` (active subscriptions), `income` (recurring income, or an untracked repeating credit), `likely` (habits with confidence >= 0.6, one expected date each; up to 2 days late shows as today), each with a stable `id`. `watch`: `category_hot` (over its budget, or 1.25x its usual and Rs 500 more), `unusual` (robust z >= 3.5 against the payee's or category's earlier spends, last 7 days) and `subscription_candidate` (untracked), minus anything with a `dismiss` row in `prediction_feedback`. A past month returns the actuals (p10 = p50 = p90), `safeToday: null` and empty lists; a future month is a 422. The route stores the requested timezone in `engine_patterns.timezone` and rebuilds the profile inline (no LLM) when it is missing, built for another timezone, or dirty for over 15 minutes; if that fails it uses the last good profile. `summary` is template text until P3's labeller; `accuracy` is `{lastMonthErrorPct}` once the previous month has been scored (null before), see Learning below.
- **DeepSeek labeller** (`labeller.ts`, migration `0011`; plan section 7): after each user's nightly rebuild the queue consumer (`handleEngineBatch`) makes ONE JSON-mode request (`responseFormat: 'json_object'` on the agent's `LlmClient`) with whichever tasks have work: one-off vs habit for unlabelled debits of at least 3x their payee or category usual and Rs 500 (`txn_labels`, source `llm`, max 15, notes trimmed to 80 characters); subscription vs habit for new subscription candidates (`payee_patterns.kind` + `kind_source = 'llm'`, kept across rebuilds while the rule still sees a habit or subscription, max 10); payee merges for similar names (`engine_patterns.payee_merges` alias -> canonical, applied in `loadEngineRows` so cadences, watch and upcoming see one payee; rejected pairs are cached in `merge_rejects`, max 10); and sentence templates for the summary line and the watch cards (`engine_patterns.copy`, `copy_day` = the user's local day). The model never writes a number: templates use `{placeholders}` and `renderTemplate` (`copy.ts`) rejects any template with a digit, currency or percent sign, number word, unknown placeholder or more than 160 characters, so the forecast falls back to its code text per card (and uses the model's text only when `copy_day` is today and the card's situation still matches). Templates may hold only Latin letters and plain punctuation, must use each placeholder once, set off from letters, and may not contain number words (English or Hinglish), links or UPI words; they are stored per card id and variant (`hot:<id>|over`). Merges skip payees the user dismissed or decided, payees with learned confidence, and pairs from different categories; `unmerge(db, userId, alias)` undoes one (for the feedback endpoint) and rejects the pair. With the labeller on, the nightly fan-out also queues recent non-learning profiles that have no copy for today. A timed-out or aborted call keeps its token reservation; a refused one (4xx, 5xx, no connection) gives it back. A new one-off label or merge triggers one more rebuild (without the model). Off by `ENGINE_LLM_ENABLED=false`; spend is capped by `ENGINE_DAILY_TOKEN_BUDGET` (default 2,000,000 prompt + completion tokens per UTC day across all users, `engine_usage`: each call reserves an estimate with an atomic upsert-with-WHERE and settles to the real usage). A failed or invalid answer writes nothing and never fails or retries the queue message.
- **Learning** (P4: `confidence.ts`, `feedback.ts`, `scoring.ts`, `backtest.ts`; plan section 6):
  - **Feedback**: `POST /api/v1/predictions/feedback` `{targetKind, targetId, verdict, timezone?}` answers 204 (the app refetches `/forecast`); the latest answer per target (per month for `category_watch`) is stored in `prediction_feedback`, which hides dismissed cards; sending the same verdict again is a no-op, so a replay cannot inflate confidence. Boosts decay the old evidence first. `payee` (id = `payeeKey`): `confirm` adds 3 to alpha (after decay, see below), `dismiss` suppresses the payee. `subscription_candidate` (`payeeKey`): `confirm` makes it a subscription (`kind_source = 'user'`, alpha + 3; the app sends it once the user has saved the recurring item it opened prefilled from the card's `name`, `cadence` and `amount`), `dismiss` = not a subscription, a habit. `unusual_txn` (transaction id): `one_off` or `not_one_off` write the user's label (`txn_labels`, source `user`, always replaces the model's) and rebuild; every answer (`one_off`, `not_one_off`, `dismiss`) hides the card. `category_watch` (category id): `dismiss` hides it for the current local month only (`timezone` picks the month, else the engine's). `payee_merge` (the alias `payeeKey`): `dismiss` undoes the model's merge (`unmerge`). A verdict the kind does not take is a 422, so is a target that is not the user's (a payee they have no pattern for, another user's transaction, ...). The labeller never overrides a user's label or `kind_source = 'user'`.
  - **Implicit hits and misses** (`scoreExpectations`, run first in every `runEngineForUser`): a habit or subscription whose expected date + 2 days is over is a hit (a later debit of the payee within +-2 days: alpha + 1) or a miss (beta + 1). Before each update alpha and beta are multiplied by 0.9 and alpha + beta is capped at 20 (both scaled down together), so a payee that changed loses trust in a handful of misses. `payee_patterns.last_scored_expected_at` makes each expectation count once (every past date of a payee that stays away is judged, up to 8 per run, and the next expected date moves on by one interval), and a row with a score or any learned confidence is kept (inactive) rather than pruned. Confidence = alpha / (alpha + beta); below 0.4 a payee is hidden, below 0.6 it is not a likely spend.
  - **Self-scoring**: `handleEngineBatch` calls `runScoring` after the rebuild. On the user's local day 1, 7, 14 and 21 it then saves the current month's landing range as a `forecast_snapshots` row (`method = 'stats'`, with the `width_factor` and `window_days` in force, not in learning mode, `INSERT OR IGNORE`); the fan-out queues every active non-learning profile within a day of those days on the IST date, the job decides by the user's own day. Any finished month with snapshots missing an `actual` gets the month's debit total (the same definition as `spentSoFar`); whenever the latest finished month with actuals is newer than `engine_patterns.last_tuned_month` (so a failed night is retried) and there are at least 2 scored months, `width_factor` is multiplied by 1.1 (cap 2.5) if fewer than 70% of the scored snapshots made with the current width (at least 4 are needed) had the actual inside p10..p90, or by 0.95 (floor 0.6) if over 90% did with a median error of at most 10%; and `window_days` becomes the one of 60, 90 and 120 whose replay of that month (days 7, 14, 21, `forecastFlexibleAsOf`) had the lowest mean error on the flexible spend still to come. Both live on `engine_patterns` (migration `0010`) and a rebuild only reads them.
  - **Accuracy**: `GET /api/v1/forecast/accuracy` returns `{months: [{year, month, errorPct, covered}]}`, the last 3 scored months, newest first (`errorPct` = |p50 - actual| / actual in percent, one decimal, from the day-14 snapshot (a month without one is not listed); `covered` = the actual was inside p10..p90). The forecast's `accuracy.lastMonthErrorPct` is the previous calendar month's.
  - **Backtest** (read-only): `npm run engine:backtest -- --user <id> --months 3 [--days 7,14,21 | --daily] [--window 90] [--width 1] [--persist-to .wrangler/state/v3]` opens the local D1 (the state `wrangler dev` keeps; `npx wrangler d1 migrations apply DB --local` first if it is new) through `getPlatformProxy`, replays each complete month as of the start of each chosen day from the rows known then (recurring bills read from the rows, so only the flexible part is judged) and prints p10/p50/p90, error and inside/outside per forecast, then the median error and coverage. It prints wrangler's startup notes first; a user without enough history reports 'not enough history'.

## AI agent (v3: SQL agent)

`features/agent/`, contract C9 in `../docs/rewrite/agent-v2.md` (unchanged). The agent is a bounded tool-calling loop in which the model reads a schema context, writes SQLite SELECTs, runs them, fixes errors and answers in plain language.

```
POST /api/v1/agent/chat   requireAuth -> AI_LIMITER -> body limit (1 MiB) -> zod -> bad timezone 400
                          -> kill switch (AGENT_ENABLED) -> daily token budget -> daily questions (429) -> turn
turn: pre-pass (no LLM) -> [ DeepSeek call -> run_sql / find_entities / ... ]* -> answer -> numeric verification -> blocks + memory
```

- **Pre-pass** (`prepass.ts`, `range.ts`, `entities.ts`): a time hint from the question ("June 2026", "last 7 days"; none when a comparison, a day of month or two separate months make it ambiguous) or from the memory, and fuzzy entity resolution with trigram similarity (`trigram.ts`, a TypeScript port of pg_trgm) over the user's payees and categories. A name that matches two payees (or categories) equally and exactly neither ends the turn with "Did you mean A or B?" and no model call. Matches go to the model as keys, so it can use them in SQL right away.
- **Loop** (`service.ts` `runAgentTurn`): the model (`AGENT_MODEL`, non-thinking, temperature 0, function calling) calls tools; the calls of one step run together (max 3, the rest get an error result). At most `AGENT_MAX_STEPS` (6) tool steps and 12 `run_sql` calls per question, then the model must answer (`tool_choice: none`, tool list unchanged, so the prefix cache holds). Turn deadline `AGENT_TURN_TIMEOUT_SECONDS` (25 s) and `AGENT_LLM_TIMEOUT_SECONDS` (12 s) per model call, enforced with `AbortSignal`; `AGENT_MODEL_FALLBACK` is tried once, only while at least 4 s remain. With query results in hand, a model failure or the deadline yields the fallback answer; without any, the C5 error.
- **Tools** (`tools.ts`, zod schemas are the single source of truth for the JSON Schema sent to DeepSeek and for validating the arguments): `run_sql {sql, purpose}` -> `{result_id, columns, rows (first 50), row_count, truncated}` or `{error}` (the SQLite message, so the model can fix and rerun); `find_entities {phrases}`; `link_transactions {filter payee | category | day, ...}` (the server checks the key or id belongs to the user and builds the TransactionsList deep link; the last valid one wins); `show_chart {kind, result_id, label_column, value_columns}` (a chart built from an earlier `run_sql` result, max one per turn). `purpose` is the SSE `step` label.
- **SQL guard** (`sql-guard.ts`, the security core; `schema-context.ts` is what the model reads). The model's SQL never touches a real table: it runs as `SELECT * FROM (WITH <views>, <shadows>, <model CTEs> <model query>) LIMIT 201`. SQLite resolves unqualified names to CTEs first, so `transactions`, `categories`, `budgets`, `category_budgets`, `recurring_items` are views bound to the user (`?1`), without `user_id`, notes, receipts, voice, payment hash or deleted rows, with money in rupees and `local_date` / `local_at` computed from the user's UTC offset (`core/timezone.ts` `utcOffsetMinutes`, fixed at query time: fine for India, off by an hour across a DST change). EVERY other table (`users`, `auth_sessions`, `notifications`, `jobs`, usage tables, `d1_migrations`...) is shadowed by an empty CTE; `test/agent-sql-guard.test.ts` fails when a migration adds a table that is neither exposed nor shadowed. A lexer (strings, comments and quoted names handled; the executed text is rebuilt without comments) enforces one SELECT/WITH statement of at most 4 000 characters, balanced parentheses, no bind parameters, none of `ATTACH DETACH PRAGMA INSERT UPDATE DELETE REPLACE( CREATE DROP ALTER VACUUM REINDEX ANALYZE RECURSIVE BEGIN COMMIT ROLLBACK SAVEPOINT RELEASE`, no `main` / `temp` anywhere (a schema qualifier would bypass the CTE lookup), no `sqlite_*`, `_cf_*`, `pragma_*`, `load_extension`, `readfile`, `writefile`, `randomblob`, `zeroblob`, `dbstat`, and no model CTE named like a table. Rows are capped at 200 (`truncated`), each query races a 3 s timeout and the turn signal.
- **Prompt** (`prompts.ts`): static system prompt (rules + schema context), static tool list, then ONE user message with memory, earlier user questions (<= 3 turns, <= 1.5k chars; client assistant text is never used), the server-resolved block, the NOW block and the question. Tool results are `tool` messages wrapped in `<data tool="...">`.
- **Answer verification** (`verify.ts`): every amount (₹ / Rs / INR, lakh / crore / k), percentage and number >= 1000 in the answer must be one of the numeric cells of the `run_sql` rows the model was shown (commas of either grouping, whole-rupee rounding, shorthand rounded to its precision). On a mismatch the model regenerates ONCE (non-streamed, `tool_choice: none`, told which figures failed); still wrong gives the deterministic fallback (`fallback.ts`: "Here's what I found:" and up to 5 rows of the last result, money with Indian grouping) or the no-data apology. `final.answer` is authoritative.
- **Chart and deep link** (`blocks.ts`, `deep-link.ts`): built from `run_sql` results and database names, never from model text; both go through the contract's schema validation (`chart.ts`).
- **Memory** (`memory.ts`): `memory` = `base64url(payload).base64url(HMAC-SHA256)` signed with `AGENT_MEMORY_SECRET`; payload `{v, user_id, time_range, entities, last_tools, summary <= 300, exp}`, 24 h. Verified for signature, user and expiry; anything else is ignored (the turn runs without memory). Without the secret the feature is off (`memory: ""`).
- **Budget and kill switch** (`usage.ts`): `AGENT_ENABLED=false` answers `agent_disabled`; `agent_usage` (one row per user and UTC day, atomic upsert-increment) holds prompt + completion tokens, and a user at `AGENT_DAILY_TOKEN_BUDGET` (default 200 000) gets `daily_limit`. Each user also gets `AGENT_DAILY_QUESTIONS` (default 5) turns per UTC day: the `turns` column is incremented atomically BEFORE the turn runs (`claimQuestion`, so concurrent requests cannot exceed it, and failed or aborted turns count), and the sixth question is answered 429 with the C5 error body (`daily_limit`) and `Retry-After` until 00:00 UTC. Tokens are recorded in a `finally` on every path (success, error, client abort, timeout) after the response (`waitUntil`); a failed read or claim fails open.
- **Responses** (C9). JSON (default): the C5 `ChatResponse` `{answer, blocks, deep_link}` plus `memory` and `turn_id`. SSE (`Accept: text/event-stream`, Hono `streamSSE`): `step {tool,label}` per tool call, `delta {text}` while the answer streams, then `final` (the JSON response, authoritative) or `error {code,message}`; events are written in order and a client disconnect aborts the turn. Failures are C5 bodies (HTTP 200 `{"error": {"code": "assistant_busy" | "assistant_error" | "agent_failed" | "agent_disabled" | "daily_limit", "message"}}`, or the `error` event); a bad timezone is 400, an unreachable database 503 + `Retry-After` in JSON mode (an `assistant_busy` error event in SSE).
- **Feedback**: `POST /api/v1/agent/feedback {turn_id, rating: "up" | "down", comment?}` upserts one row per (user, turn) into `agent_feedback` (JWT user id) and answers `{"ok": true}`.
- **Observability**: one `agent_turn` log line per turn (hashed user, tool steps with ms / rows / ok, model calls with prompt, cache-hit and completion tokens, total ms, `verified` = pass | regenerated | template, outcome; `run_sql` steps carry the SQL length and the SQLite error, never the query or rows). `X-Agent-Debug: 1` returns the same as `debug` in the response (used by the evals; no user data).
- **Database**: tables `agent_usage` (daily token budget, atomic `INSERT ... ON CONFLICT DO UPDATE`) and `agent_feedback` live in `migrations/0001_init.sql`. `queries.ts` holds the database seams (`run_sql` through the guard, `resolve_entities`, `link_target`), always bound to the user id of the verified token. `resolve_entities` (`entities.ts`) scores the user's most used 400 `(payee_key, name)` pairs and the visible categories with a TypeScript port of pg_trgm `similarity()` / `word_similarity()` (`trigram.ts`, threshold 0.4).
- **Tests**: `test/agent-*.test.ts` (the SQL guard with two users and every injection trick, loop, DeepSeek client incl. streaming chunks, memory, pre-pass, verification and fallback, tools and blocks, the pg_trgm port, the eval fixtures, routes incl. SSE framing, feedback, kill switch, budget).
- **Evals**: `evals/` (see `evals/README.md`): D1 fixture seed, 109 golden conversations with reference SQL, a runner with metrics and reports, `.github/workflows/agent-evals.yml` (weekly + manual).

## Email (R4)

`features/email/`: welcome, weekly/monthly digests, unsubscribe.

- **Claim / reclaim** (`sends-repository.ts`): insert `email_sends` `pending` with `claimed_at`; only a unique violation means "already claimed" (any other error propagates); then a conditional update reclaims a `pending` row older than 30 minutes. Send success -> `sent` (+ Brevo message id); failure -> the pending row is deleted.
- **Welcome**: `createEmailService(env, db).sendWelcomeIfNeeded` (called by `GET /me` through `waitUntil`) needs `BREVO_API_KEY` and `EMAIL_UNSUBSCRIBE_SECRET` (missing -> logged skip; S3: there is no fallback secret), claims `(welcome, once)`, sends, marks sent; a failed send releases the claim and is only logged.
- **Digest fan-out** (`digest.ts`): cron `30 2 * * *` (08:00 IST) -> `dueDigestKinds` (Monday -> weekly, 1st -> monthly, both when they coincide; IST calendar day) -> page `user_settings` where the flag is on (1000 per page, stable order) -> `EMAIL_QUEUE.sendBatch` of `{type: 'digest', user_id, kind, period_key}` in batches of at most 100. Period keys as in Python: `YYYY-Www` (previous Mon-Sun, ISO week) and `YYYY-MM` (previous month). `POST /api/v1/internal/email/run {kind}` (`X-Email-Cron-Secret`, constant-time compare, rejected when the secret is unset) enqueues the same messages and answers `{sent, queued}` (both are the number queued: delivery is asynchronous).
- **Consumer** (`consumer.ts`, queue `dime-email`, DLQ `dime-email-dlq` handled by `handleEmailDlq`, which logs `email_digest_dead_lettered` and acks; every failed attempt already released its claim): per message `sendDigest` = look up the address, claim, build the payload from SQL aggregates (period summary incl. debit-by-category, payee totals, top 5 debits, budget; no per-row loops), render, Brevo, mark sent. A failure releases the claim; transient errors (Brevo 408/425/429/5xx, network, DB hiccup) `retry({delaySeconds: 30 * 2^(attempt-1), max 600})`, permanent ones (Brevo refusal) are logged and acked. One FavQs request per batch (2 s timeout, fallback pool).
- **Unsubscribe**: `GET /api/v1/email/unsubscribe?token=` (HTML page, or `400 {"detail": "Invalid unsubscribe link."}`; `422` for a token shorter than 8). Tokens are byte-compatible with Python (`user|kind|issued|hmac_sha256_hex`, 90 days); `test/email-core.test.ts` pins vectors generated by the Python implementation.
- **Static assets**: the five welcome postcards live in `public/email/` and are served at `/email/*` by Workers Static Assets (no Worker CPU). Emails use `EMAIL_ASSET_BASE_URL` when set, else `EMAIL_PUBLIC_BASE_URL/email`. Set `EMAIL_ASSET_BASE_URL` to host them elsewhere. `/static/email/*` (the old Python mount) 301-redirects to `/email/*`.
